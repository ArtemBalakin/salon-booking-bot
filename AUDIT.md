# Аудит проекта salon-booking-bot

Дата проверки: 13 октября 2026 г.

## Что проверено

- Исходники Java, Telegram-бота, REST API, JPA/репозиториев, Flyway-миграций и Mini App.
- Конфигурация Spring, Dockerfile, docker-compose и шаблон `.env.example`.
- Базовая защита от дублей записей: транзакция и `PESSIMISTIC_WRITE` для слота, частичный уникальный индекс `uq_booking_active_slot`.
- Проверка наличия явных секретов в файлах, включённых в Git.
- Java: девять автономных проверок классов `ClientInput` и `TelegramInitDataValidator` (`javac --release 17` + `java`) прошли.
- JavaScript: `node --check` прошёл.
- YAML: файлы синтаксически разобраны.
- Git: `git diff --cached --check` прошёл; в коммит не включены `.idea/` и `target/` из входного архива.

**Не удалось проверить:** Maven `clean verify`, интеграцию с PostgreSQL, сборку Docker, обмен с реальным Telegram. В рабочей среде нет Maven и Docker, а Maven Central недоступен; для проверки полного проекта добавлен GitHub Actions CI, который выполнит `mvn clean verify` после публикации. Поэтому этот аудит не означает, что проект готов к выпуску.

## Внесённые изменения

1. Проверка Telegram `initData` теперь отвергает устаревшие (более 24 часов), будущие, некорректные и содержащие повторяющиеся поля данные, сравнивает подписи без обычного сравнения строк.
2. В Mini App строки из базы выводятся через безопасный DOM (`textContent`), не через HTML-конкатенацию.
3. Для запросов мастеров/слотов предотвращено отображение устаревших ответов и добавлены пользовательские сообщения об ошибке сети.
4. POST создания записи проверяет наличие корректных `serviceId` и `slotId`.
5. Усилены `.gitignore`/`.dockerignore`, исключён локальный файл настроек Maven со ссылками на внутреннюю инфраструктуру.
6. Добавлены unit-тесты валидатора и workflow CI; Dockerfile больше не отключает тесты при сборке.
7. Для платформ с динамическим портом используется `${PORT:8080}`; обновлён README.

## Известные риски (приоритет)

### P0 — до подключения клиентов

- **Длительность услуг игнорируется.** Услуги на 90 и 120 минут занимают только один слот на 60 минут, поэтому следующий клиент может забронировать пересекающееся время. Нужно планирование произвольных интервалов, запрет пересечений на уровне БД/транзакций, тесты на параллельные запросы.
- **Демо-данные.** Миграция V2 создаёт пример мастеров и услуг. Их необходимо заменить, настроить реальные графики, выходные и исключения; миграции нельзя просто переписывать на базе с уже применённым Flyway.

### P1 — надёжность и поддержка

- **Telegram-уведомления без outbox.** Отправка при сбое Telegram может потеряться: вызовы `safeExecute` логируют ошибку и не сохраняют задачу для повторной отправки; напоминания помечаются отправленными. Нужна таблица событий, ретраи с backoff, идемпотентность.
- **Устаревший Spring Boot 3.3.4.** Ветка 3.3.x вышла из OSS-поддержки 19 июня 2025. Планируется обновление до поддерживаемой ветки после прохода полного CI и проверки миграций.
- **Нет rate limiting для POST `/api/bookings`.** Подпись защищает от анонимной записи, но один авторизованный пользователь может создавать много записей. Нужны лимиты на Telegram user ID и предотвращение спама.
- **Один экземпляр.** Long polling и scheduler выполняются в одном процессе, поэтому не запускать несколько реплик без распределённых блокировок/разделения фоновых задач.
- **Данные клиентов:** обязательны резервные копии PostgreSQL, ограничение доступа, сроки хранения персональных данных и контроль доступа к админ-функциям.

### P2 — функциональные возможности

- Нет полноценной админки, переноса записи, собственного графика по мастерам, праздников и отпусков.
- Отображение даты в Mini App зависит от местного часового пояса устройства пользователя, тогда как сервер привязан к `APP_TIMEZONE`.
- Слабое покрытие интеграционными тестами (сейчас только базовые unit-тесты).
